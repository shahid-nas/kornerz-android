## Why

> **See also:** [`docs/architecture.md`](../../../docs/architecture.md) for the MVVM + Repository + UDF contract, `AsyncValue<T>`, `Channel<NavEvent>`, module boundaries, Hilt scopes, and the canonical library list that every artifact in this change conforms to.

Phases P0–P9 shipped a populated Home, Kornerz, Nooks, Loops, Profile, Notifications, Admin, Premium, and Video-call surface on the shared Firebase backend (`kornerz-72fba`). P10 is the closing phase: it turns the last two stubs into live screens and turns the app from "feature-complete" to "demo-complete". The iOS build already has all three verticals — the **Klouders leaderboard** (`HomeVC/Ranking/`), the **deep-link router** (`DeepLinks/`), and the shared **polish views** (`Components/RetryView.swift`, `Components/NoDataView.swift`, `Components/LoadingMoreView.swift`) — and P10 is the Android port of them.

An audit of the Android tree before scoping this proposal found **six defects and four open stubs** that make the P10 demo claim literally untrue today:

1. **The Klouders tab is a placeholder.** `feature/shell/.../AppShell.kt:658-659` registers `kloudersTabGraph` as `tabComposableWithLogout(ShellTab.Klouders, onLogout)` — the P0 `EmptyTabScreen` stub, rendering the literal text `"Coming in Phase 7"`. iOS's fifth tab is the live leaderboard (`AppTabController.swift:137-142` → `RankingViewController`). No `feature/ranking` module exists.
2. **The leaderboard reads the wrong Firestore field, so every score is zero.** `GamificationRepository` (`core/network/.../gamification/GamificationRepository.kt:140`) declares `FIELD_POINTS = "gameficationPoints"`. iOS `Models/Gamification.swift:23` maps `points` → **`"gameficationQtdPts"`**. The Android field name does not exist on any `Gamefication` document, so `doc.getLong(FIELD_POINTS)` is always `null` and every row sums to `0`. This also breaks the **points chip in the tab header** (`core/ui/.../header/TabHeader.kt:123` → `getUserPoints()`), which has been silently rendering `0` on Home, Kornerz, Nooks, and Loops since P2.
3. **The leaderboard never resolves user names.** iOS `GamificationService.fillUserInformation` (`:142-152`) queries `Users` where `codeUser in [userIds]` and assigns `userName = user.nickName`. The Android `getRanking` (`:88-93`) hardcodes `userName = "User"` — every row of the leaderboard would read "User".
4. **Notification deep-link types never parse.** iOS `DeeplinkType` (`DeepLinks/DeeplinkManager.swift:56-64`) uses the raw values `NewEvent`, `NewArticle`, `NewForum`, `VideoCall`, `NewComment`, `NewLoop`, `LoopComment` — capitalised. Android `UserNotificationDeeplinkType.fromRaw` (`core/model/.../UserNotification.kt:62-71`) matches the **lower-camel** spellings `newEvent`, `newArticle`, … . The comparison is case-sensitive, so a real `notificationType` of `"NewLoop"` parses as `UNKNOWN`. Every notification in the app is therefore unroutable today, and `UserNotification.deeplink(with:)` returns `null` for all of them.
5. **The `kornerz://` scheme is minted but never consumed.** `UserNotification.deeplink(with:)` (`core/model/.../UserNotification.kt:80-90`) already builds `kornerz://loop/{id}`, `kornerz://forum/{id}`, and `kornerz://community/{id}/{event|article|forum|call}` URIs, but `app/src/main/AndroidManifest.xml` declares **no** `<intent-filter>` for the scheme, there is no deep-link manager, and the notifications screen's `onOpenDeeplink` handler shows a `"Deeplink coming in Phase 10"` snackbar (`feature/shell/.../AppShell.kt:324-328`).
6. **A tapped push notification goes nowhere.** `KornerzFcmService` (`app/.../fcm/KornerzFcmService.kt:52-58`) builds the tray notification's `PendingIntent` from `packageManager.getLaunchIntentForPackage(...)` — a tap opens the app and stops. iOS routes the tap payload straight into the deep-link router (`AppDelegate.swift:170-175` → `DeepLinksManager.shared.handleDeepLink(info:)`).

The three open stubs: there is no `LoadingMoreView` / `NoDataView` / `RetryView` equivalent in `core/ui` (the pagination footer is an inline `CircularProgressIndicator` in `NotificationsContent`, and each screen rolls its own error state); the release build runs with `isMinifyEnabled = false` in both build types (`app/build.gradle.kts:41,51`) and `proguard-rules.pro` carries no Vonage or Firebase keep rules; and the module-boundary rule from `docs/architecture.md` §2.5 has no enforcement mechanism beyond the dependency graph.

Phase 10 ports the three verticals, fixes the six defects, and closes the P10 exit checklist. Backend integration is real (`kornerz-72fba`), no mock servers, and the phase ships an APK that compiles, launches, and is presentable to all stakeholders for the "feature-by-feature parity demo against iOS" (`docs/phases.md:400`).

### iOS audit findings that scope this proposal

The iOS source was audited before scoping. Six findings materially changed the plan:

1. **Only 3 of iOS's 7 deep-link types are routable on Android.** iOS `DeepLink` (`DeepLinks/DeeplinkManager.swift:13-54`) enumerates `newEvent`, `newArticle`, `newForum`, `newComment`, `newLoop`, `newLoopComment`, and `videoCall`. The Android port deliberately excludes Event Detail, Post Detail, Forum Detail, and the Article/Event/Forum creation wizards — 9 screens dropped as dead code by stakeholder review on 2026-10-07 (`docs/screen-inventory.md:229-237`). Phase 10 therefore routes `newLoop`, `newLoopComment`, and `videoCall` to live destinations, and gives the other four a single, explicit "not available in this build" path instead of a crash or a silent no-op. It does **not** resurrect the dropped screens.
2. **iOS's `videoCall` deep link opens the Korner detail, not the call.** `DeeplinkViewController.handleCallLink` (`:135-155`) fetches the community and pushes a `KornerDetailController`. The call itself is still entered from the Korner detail. Android mirrors this exactly — the deep link lands on the Korner detail, and the P9 video-call surface stays reachable only from there.
3. **iOS's `UserNotification.deeplink(with:)` has a copy-paste bug on `newComment`.** `Models/UserNotification.swift:65-67` returns `.videoCall(...)` for the `.newComment` case. It is unreachable in iOS because `NotificationsViewModel.notificationOpened` (`:120-127`) short-circuits `.newComment` before calling `deeplink(with:)`. The existing `user-notification-domain` spec already flags this and says "P10 polish will correct it". Android **does not** port the bug: `newComment` resolves to the forum route. This is the one intentional behavioural divergence from iOS, and it is recorded in the spec.
4. **iOS has two distinct deep-link payload dialects, and Android must too.** The *Firestore notification document* carries `notificationType` / `notificationReferenceId` / `notificationCommunityId`; the *FCM push payload* carries `pushType` / `communityId` / `eventId` / `articleId` / `forumId` / `loopId` (`DeeplinkManager.handleDeepLink(info:)` `:85-134`). The in-app list mints a `kornerz://` URI from the first; a tapped tray notification routes from the second, with no community fetch. Android keeps both dialects distinct rather than flattening them.
5. **iOS's `getRanking` resolves names in a second query and assigns medals by index.** `GamificationService.getRanking` (`:106-140`) sorts by points, truncates to `count`, then calls `fillUserInformation` (`Users.whereField("codeUser", in: userIds)`) and `fillMadalInformation` (`:154-166`), which assigns gold/silver/bronze to the first three rows of the final sorted list. The Android port skips the name query entirely (defect 3) and must add it. iOS's own sort is unstable and its tie order is therefore arbitrary; Android's `sortedByDescending` is stable, so ties resolve deterministically by first-seen order — a deliberate, documented improvement, not a parity break.
6. **`Gamefication` is misspelled in the backend.** iOS `GamificationService.swift:27` reads `db.collection("Gamefication")` and `Models/Gamification.swift` keys every field with the same `gamefication` prefix. Android already preserves the collection name (`GamificationRepository.kt:137`), but has never modelled the document itself. Phase 10 adds the `Gamification` model with the iOS `@SerialName` mapping so the field names cannot drift again — the direct cause of defect 2.

Two further iOS artifacts are deliberately **not** ported: iOS's `RankingViewController` shows a `SVProgressHUD` spinner overlay (Android uses the shared `KornerzLoadingView`), and the iOS ranking table header is a `List` `Section` header reading `#` / `Name` / `Points` (Android reproduces it as a sticky row in the same `LazyColumn`). The `medal-gold` / `medal-silver` / `medal-bronze` assets are ported as Android vector drawables from the iOS SVG sources (`Kornerz/Resources/Assets.xcassets/Images/Medal/`).

## What Changes

### A — Klouders (Ranking) tab: screens 2.6 + 2.7

- Add a new `feature/ranking` Gradle module (`namespace = "com.kornerz.feature.ranking"`, mirroring `feature/profile/build.gradle.kts`) hosting the P10 ranking vertical, wired into `settings.gradle.kts` and `app/build.gradle.kts`. The module is imported by `app` only, per `docs/architecture.md` §2.5; `feature/shell` reaches it exactly the way it reaches `feature/subscription` in P8 — via a route contributed from the composition root.

- Add `Gamification` (`@Serializable`, Compose-free) to `core/model` — the `Gamefication/{id}` document, mirroring iOS `Models/Gamification.swift` field-for-field: `gameficationId`, `gameficationAction`, `gameficationDateHora`, **`gameficationQtdPts`**, `gameficationUserId`, `gameficationReferenceId`. The misspelling is preserved verbatim on both sides.

- Add `Rank` to `core/model` — the leaderboard rank tier, promoted out of `UserRanking.Medal` so the medal vocabulary is a first-class domain concept rather than a nested enum on a row model. `UserRanking` keeps its `userId` / `userName` / `points` / `medal` shape but its `Medal` enum is replaced by `Rank`.

- Fix `GamificationRepository.getRanking(count)` — **the blocking defect 2**: read points from `gameficationQtdPts`, not `gameficationPoints`. Add the missing iOS `fillUserInformation` step (defect 3): batch-fetch `Users` where `codeUser in [userIds]` and assign each row's `nickname` as its `userName`, leaving `"User"` as the fallback for a user id that no longer resolves. Assign medals by final sorted position (gold / silver / bronze for the first three, `NONE` after), mirroring iOS `fillMadalInformation`.

- Fix `GamificationRepository.getUserPoints()` with the same field-name fix. This restores the points chip in the shared tab header (`core/ui/.../header/TabHeader.kt:123`), which has read `0` on every tab since P2.

- Add `RankingScreen` + `RankingContent` (2.7) in `feature/ranking/list/` — mirrors iOS `RankingScreen.swift` (76 lines) exactly: a plain list whose `Section` header row reads `#` / `Name` / `Points` in three fixed 75-pt columns; one row per leaderboard entry with a 40-pt medal or rank numeral in a 75-pt leading slot, the user's name in bold, and the points count right-aligned in a 75-pt trailing slot; no separators; and a fetch-on-appear. The numeral slot uses `onSurfaceVariant` at 16-pt bold, exactly as iOS does for a non-podium row.

- Add `RankingViewModel` (`@HiltViewModel`) in `feature/ranking/list/` — the UDF contract for 2.6/2.7. Exposes `RankingState(rankings: AsyncValue<List<UserRanking>>)` and loads the **top 10** rows, matching iOS `RankingViewModel.fetchRankings()` (`:51-70`, `gamification.getRanking(10)`). The screen title is `"Klouders"` (iOS `RankingViewController.configureNavigation` reads the `klouders` localization key).

- Replace the `kloudersTabGraph` placeholder in `feature/shell` with the real ranking screen, and drop the P0 `EmptyTabScreen` "Log out" affordance that only existed as a placeholder for the P1 logout path — P1 shipped a real logout in P6.

### B — Deep links: screen 13.1 + routing (cold start + warm)

- Add a typed `DeepLink` sealed interface to `core/model`, mirroring iOS `DeepLinks/DeeplinkManager.swift:13-54` case-for-case (`NewEvent`, `NewArticle`, `NewForum`, `VideoCall`, `NewComment`, `NewLoop`, `NewLoopComment`), with the entity ids iOS carries. `DeepLink` gains `toUri()` and a companion `parse(uri)`, establishing the `kornerz://` URI grammar as the transport form of the typed model.

- **Fix defect 4**: `UserNotificationDeeplinkType.fromRaw` SHALL parse the iOS raw values (`NewEvent`, `NewArticle`, `NewForum`, `VideoCall`, `NewComment`, `NewLoop`, `LoopComment`) case-insensitively, so the existing capitalised server values parse and the legacy lower-camel spellings keep working. `UserNotificationDeeplinkType` is reconciled with the new `DeepLink` cases one-for-one.

- **Change** `UserNotification.deeplink(with: Community?)` from returning a `String?` URI to returning a `DeepLink?`, matching the contract the existing `user-notification-domain` spec already describes (`.newEvent(EventRef(eventId, communityId))`, `.newLoop(LoopRef(communityId, loopId))`, …). The iOS field requirements are honoured exactly: `newEvent` / `newArticle` / `newForum` require both `reference` and the community id, `newLoop` requires both, `loopComment` requires `reference` only, `videoCall` requires the community id only. The iOS `newComment → videoCall` bug is **not** ported.

- Add a `DeepLinkManager` (`@Singleton`) in `feature/shell` — the Android counterpart of iOS `DeepLinksManager`, with the same three responsibilities: `handle(deeplink)` (accept a link), `notifyAppLaunch()` (the app is ready to route), and `handlePendingDeeplink()` (route the held link once the app is loaded). It holds the pending link so a **cold start** from a deep link does not drop the intent while the splash → auth → shell chain is still resolving.

- Add a `DeepLinkResolver` in `feature/shell` — maps a typed `DeepLink` to a routable destination, or to a "not available in this build" outcome for the four types whose screens are excluded from the Android port. This is the single place that knows which deep links are live.

- Add the deep-link interstitial (13.1) as a top-level `deeplink/resolving` route on the shell's root `NavHost`, rendered above the bottom bar. It mirrors iOS `DeeplinkViewController` (371 lines): a transient full-screen route that resolves the incoming link and then navigates to the real destination, removing itself from the back stack — exactly what iOS does with `removeSelfFromNavigation()` (`:41-49`). Android does not duplicate iOS's entity pre-fetch; the destination screen's own error state (standardized in the polish pass) is the single failure surface. A link that cannot be routed shows the iOS-parity alert text "Failed to load deeplink. Will navigate back to home screen" and returns the user to the Home tab.

- Register the `kornerz://` scheme in `app/src/main/AndroidManifest.xml` with an `<intent-filter>` on `MainActivity` covering the `loop`, `forum`, and `community` hosts, so an externally-fired URI reaches the app.

- Wire **warm** deep links in `MainActivity.onNewIntent` and **cold** deep links in `MainActivity.onCreate` (`intent.data`), handing the URI to the `DeepLinkManager` via a Hilt entry point (the P8 `PremiumGateEntryPoint` precedent). The shell calls `notifyAppLaunch()` once its `NavHost` is composed, which releases a link that arrived before the app was ready.

- **Fix defect 6**: the tray notification's `PendingIntent` in `KornerzFcmService` carries the deep link built from the **FCM push payload** (`pushType` + `communityId` + the entity id), matching iOS `AppDelegate.userNotificationCenter(_:didReceive:)` (`:170-175`) → `handleDeepLink(info:)`. The push dialect is kept distinct from the in-app document dialect (audit finding 4).

- Wire the notifications screen's `onOpenDeeplink` handler (currently a `"Deeplink coming in Phase 10"` snackbar) to the real resolver, so a tapped in-app notification row navigates to the resolved destination.

### C — Polish

- Add three shared components to `core/ui/components/`, each mirroring its iOS counterpart: `KornerzRetryView` (`Components/RetryView.swift` — a centered 12-pt error message over a grey-tinted capsule "Retry again" button), `KornerzNoDataView` (`Components/NoDataView.swift` — a 75-pt illustration over a Satoshi-14 title), and `KornerzLoadingMoreView` (`Components/LoadingMoreView.swift` — a centered spinner beside a "Loading more items" label). `KornerzEmptyState`, `KornerzErrorState`, and `KornerzLoadingView` already exist and are kept; the new components are the iOS-named variants the screens standardise on.

- Standardise the pagination footer across the list screens onto `KornerzLoadingMoreView` (today it is an inline spinner in `NotificationsContent` only), and standardise the empty and error surfaces onto the shared components.

- Accessibility pass: every icon-only control carries a content description; the ranking row's medal, rank numeral, name, and points are announced as one node with a spoken position; text respects the system font scale (no fixed-height text containers); and the bottom bar's items keep their labels as TalkBack descriptions.

- Performance pass: measure and record cold-start-to-first-frame, enable the release build's R8 minification and resource shrinking, and verify the release APK still assembles and launches.

- Add the missing ProGuard / R8 keep rules for the Vonage video SDK and the Firebase SDKs to `app/proguard-rules.pro`, and turn `isMinifyEnabled` / `isShrinkResources` on for the release build type (both are currently `false`).

- Enforce the module-boundary rule from `docs/architecture.md` §2.5 at compile time — `core/*` never imports `feature/*`, `feature/*` never imports `app`, and no two feature modules import each other except the documented `feature/shell → feature/*` tab-graph seam. The Gradle dependency graph is the enforcement mechanism: a violation does not compile.

- Pass the per-phase exit checklist (`./gradlew :app:assembleDevDebug`, install on API 26 + API 35 emulators, no crashes, lint, screenshots, demo walkthrough, `phase-10-end` git tag).
